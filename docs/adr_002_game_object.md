## Контекст

Все сущности (`Ship`, `Asteroid`, `Ore`, `Station`) —
независимые классы без общего предка. Способности проверялись через
`hasattr`, конфигурация — магические числа в конструкторах,
логирование — через `print()`.

Проблемы:

- нельзя написать функцию над «любой сущностью»;
- способности неявны, ошибки ловятся только в рантайме;
- баланс размазан по коду, числа дублируются;
- нет уровней логов и формата.

## Решение

1. Ввести ABC `GameObject` — единый контракт игровой сущности:
   `id`, `name`, `active`, абстрактные `update(dt)` и `draw()`.
2. Вынести способности в протоколы: `Movable`, `Drawable`,
   `Collidable` — с `@runtime_checkable`.
3. Все настройки — в `@dataclass(frozen=True)` конфиги.
4. Логирование — через `LoggingMixin` без состояния.

Правило разделения: **ABC — «чем объект является», Protocol —
«что объект умеет»**.

## Рассмотренные альтернативы

1. **Только ABC, без протоколов.**
   Отклонено: корабль одновременно `Movable`, `Drawable` и
   `Collidable` — пришлось бы городить множественное наследование
   ради ролей. Роли не должны влиять на MRO.

2. **Только Protocol, без ABC.**
   Отклонено: нет общего кода (счётчик `id`, `__init__`, свойства),
   нельзя запретить инстанцировать `GameObject` напрямую,
   нельзя заставить подкласс реализовать `update`/`draw`.

3. **Выбранное: ABC для «является», Protocol для «умеет».**
   Выбрано, потому что даёт и жёсткий контракт, и гибкие роли
   без конфликтов наследования.

## Последствия

- ✅ Единый API для всех сущностей, автоинкремент `id`.
- ✅ Способности читаются явно.
- ✅ Конфиги иммутабельны, баланс правится в одном месте.
- ✅ Логи с уровнями и форматом, легко отключаются.
- ⚠️ Больше файлов и классов — сложнее навигация.
- ⚠️ `@runtime_checkable` c `collision_radius` проверяет только
  наличие атрибута, не его тип.
- ⚠️ `__slots__` в сущностях усложняет отладку (нет `__dict__`).
